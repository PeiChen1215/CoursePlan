# 《学径 StudyPath 软件需求说明书》修改意见

- 评审对象：`D02_软件需求说明书_v0.9_20261026.md`
- 评审视角：学生使用者
- 整理日期：2026 年 10 月 28 日
- 文档性质：独立修改意见，供项目组讨论，不代表已经确认或实现。

> 优先级说明：P0 表示建议优先解决、直接影响核心流程或规则正确性；P1 表示可在核心流程完成后优化；“后续优先”表示本期暂不纳入。这些是评审建议，新增工作量仍需项目组评估。

## 一、总体意见

如果我是使用这套系统的学生，我最关心的是：今天能不能马上开始学、计划能否适应临时有事、系统会不会把没完成算成完成，以及我能不能看懂并修改它的安排。原稿的优点是课程范围明确、排程由程序完成、调整需要确认并保留版本；建议保留这些设计，并进一步明确学生的操作权、异常处理和规则一致性。

以下为基于文档的使用情境评审，不是已经开展的学生访谈或可用性测试结果。

## 三、开发范围与实施建议

保留原有选题要求对应的 P0 功能。四类智能体按职责组织，不要求四个独立常驻服务；生成任务、排程、校验和默认资源匹配均可在离线模式完成。先交付“设定目标 → 生成草案 → 解释冲突 → 确认 → 打卡 → 调整 → 查看版本”的完整流程。

完整日历、复杂动画和更多模型接入可放在 P1 或后续。不要为追求功能数量引入自动测评、多课程、推送等新模块。实施排期由项目组结合 120 学时的实际口径确认，本稿不假定新增要求没有工作量。

## 四、文档一致性补充意见

| 原稿中的具体问题 | 建议 |
|---|---|
| F-03 参考时长允许 5 分钟，3.2.1 又规定时长最小 15 分钟 | 统一存储和计算为整数分钟，分别明确参考时长、逻辑任务和排程片段的范围，避免取整后丢失时长。 |
| F-07 和响应时间表规定 10 秒超时，故障处理表又要求 5 秒切换 | 采用一致的超时预算；建议单轮累计 10 秒，已知连接失败时立即降级，重试也计入该预算。 |
| 默认预留 10% 缓冲，但容量、利用率和容量紧张阈值的计算口径不清楚 | 分开展示原始容量、缓冲和可排容量，说明利用率的分母与取整方式；给出有确定分钟数的验收例子。 |
| F-11 要保留已完成任务，又要求旧目标相关已完成任务不并入新计划 | 保留所有完成记录；服务新目标的纳入当前范围，其余放入历史区，不计入新目标完成率。 |
| F-12 将旧计划描述为随新版本归档，容易混淆计划和版本 | 同一计划保持稳定 ID，历史版本只读，当前版本继续执行；主动结束整个计划才归档。 |
| F-04 设置依赖强度，但定义和排程只支持必须满足的 AND 先修 | 本期删除不参与计算的强度字段，或明确它仅用于展示，不改变先修条件。 |
| 管理员可访问全部接口，与学生私人备注、学习安排的保护需求不一致 | 按最小必要范围授权：管理员维护课程及账号，读取学生私人计划和备注须有单独明确的业务依据。 |
| 声称不向第三方传输学生数据，但自然语言追问需要处理学生输入 | 如实说明在线模型接收哪些文本和字段，启用前由学生选择，并提供不使用在线模型的完整流程。 |
| 版本永久保留，但学习事件仅保留一个学期，可能无法还原历史进度 | 明确规划版本与执行事件的留存期限及清理方式，避免承诺无法实现的历史追溯。 |
| 部分验收例子缺少知识点时长、开始日期或固定当前时间 | 补齐输入条件及预期分钟数，保证不同测试人员能得到一致结果。 |

## 五、建议优先完成的修改

1. 修正“截止即完成”和已掌握知识点误删后继的规则。
2. 明确有严重冲突的草案不能确认，并量化时间缺口。
3. 补齐任务时长修改、单日可用时间调整和误打卡纠正。
4. 统一时长、缓冲、超时、计划状态及版本的定义。
5. 提供今日任务入口和明确的资源信息，再完善完整日历等展示功能。

学生最需要的是一份能开始执行、遇到变化能修改、能真实记录学习情况的计划。建议以这些使用场景作为需求评审和演示验收的重点。
