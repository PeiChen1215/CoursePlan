## 项目概要

本组做的是一个面向在校学生的课程学习规划辅助系统。学生选定课程、填写目标与截止日期、勾选每周可用时段后，系统把课程知识点按先修关系展开成任务，按 7:3 拆成"学习"与"练习"，再切分成不超过 2 小时的时间片，装进可用时段，并对结果做四项校验（时间不足、先修顺序、时段冲突、目标缺口）。学生确认后生成不可变版本，之后打卡、偏差、重排都会留下新的版本与事件记录。

在此基础上，本组做了三件事让它区别于"能记事的日历"：一是**多课程**——课程库可同时启用多门，学生建计划时自行选课，已确认计划占用的时间会被另一门课扣减，避免同一晚被两门课排满；二是**计划问答**——学生问"我落后了怎么办"，系统先算事实（剩余容量、逾期任务、目标缺口），再让模型用自然语言解释，模型不可用时退回模板；三是**课程测评**——管理员按知识点要点让模型出题、人工审核后发布，学生作答后选择题由程序判分、简答题由模型判分并给出理由与原文引用，报告可解释，管理员还能看到班级学情。

系统为 B/S 架构：后端 Python 3.12 + FastAPI + SQLite，前端 React 18 + TypeScript + Vite，四层结构（接口 / 服务 / 数据 / 核心），19 张表、17 个索引、13 个触发器。截至 11-18，后端 572 项测试、语句覆盖率 100%，前端 63 项测试，真实模型评测 22 条样本通过 21 条（95.5%）。

## 一、实训目的

1. **把课堂上的软件工程方法走一遍**：从需求确认、需求规格、概要设计、数据库设计、详细设计，到编码、测试、发布与总结，每份文档都有上游依据与下游承接，不做"只写不用的文档"。
2. **学会用可验证的方式表达设计**：容量公式、7:3 拆分、时间片守恒、四项校验都写成可测的规则，而不是形容词；每条关键规则至少对应一个自动化用例。
3. **理解"模型该做什么、不该做什么"**：把大模型限定在"理解自然语言、生成结构化候选、用自然语言解释"三件事上，所有数字、判断和写入都由程序完成，模型不可用时系统必须仍然可用。
4. **练习团队协作与配置管理**：按 WBS 分工、文档交叉评审、Git 分支与提交规范、缺陷登记与复测，保证四个人并行开发时不互相踩踏。

**技术要点**

- **容量核算**：可用时段展开得 C，缓冲 B=⌈0.10C⌉，可用 C′=C−B；目标闭包路径时长按知识点参考时长累加并剔除已掌握项。
- **任务分解与切片**：任务按 7:3 拆分学习/练习（用分数运算避免浮点误差，90 分钟 → 63 + 27）；单任务不超过 120 分钟，超出切片，切片合计严格等于原值（135 → 120 + 15）。
- **排程与校验**：按先修拓扑序装箱，四项校验分别产出 ERROR/WARN；确认门槛只允许无 ERROR 的草案生效。
- **跨课程时间互斥**：另一门课**已确认**版本的时间片作为忙碌区间，从本课程可用时段中扣减；草稿不占位。
- **智能体边界**：抽取、问答、出题、判分四类调用，全部有超时与降级；提示词要求输出 JSON，解析失败重试一次后降级。
- **可解释测评**：选择题程序比对答案；简答题模型给分并返回理由与引用，程序做范围校验，越界或模型不可用标"待人工复核"。

### 3.3 实施路线

1. **先立契约**：接口清单与错误码先冻结，前后端并行；接口变更必须双方确认后同步文档。
2. **先测后改**：每个缺陷先写一个失败用例，再改代码；关键算法（拆分、切片、容量、校验）的边界用例先于实现写。
3. **文档随代码走**：每次功能增量同步更新 D02/D06/D11，收尾时统一版本号并重出 Word。
4. **降级优先**：所有模型调用都有 mock 与模板兜底，断网也能完整演示主流程。

## 七、实训总结

**小组完成的成果**：一份可运行的系统（16 项功能）、19 张表的数据库、572 项后端测试与 63 项前端测试（覆盖率 100%）、16 份文档（12 份已出 v3.0 Word）、一套一键启动与重置的演示环境。

**三点体会**

1. **"能算"比"能说"难**：让页面显示一句"你落后了"很容易，难的是说清落后多少、还剩多少时间、先补哪个；把容量、拆分、校验写成可测规则，是本项目花时间最多也最值的地方。
2. **模型的边界要提前划**：一开始想让模型"顺便算一下还剩多少分钟"，结果数字不稳定；改成"程序算事实、模型只解释"之后，问答与判分都变得可复现、可解释。
3. **文档不是负担，是一致性工具**：多课程改造时，正是因为 D02 的功能条目、D06 的接口、D05 的表结构都在，才能一次改完而不漏；反过来，收尾时发现 6 份文档没跟上新功能，也说明"文档随代码走"必须落到每次提交，而不是最后补。

**对课程的建议**：希望实训中期增加一次"设计可测性"的专题讲评，我们是在写校验用例时才真正理解"规则要可判定"；另外，模板类文档（如测试计划与测试报告）如果能在中期给一份填写示例，能少走一些格式上的弯路。
