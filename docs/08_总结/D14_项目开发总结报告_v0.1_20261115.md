### 2.3 基本流程

实际处理流程（与 D04 设计一致，未发生结构性偏离）：

```
学生登录 ──▶ 填写约束（目标/截止/可用时间/已掌握）
                    │
                    ├─ 规则解析 ─┐
                    └─ 模型兜底 ─┴─▶ 容量核算 C/B/C′ ──▶ 生成草案
                                                          │
                                    闭包 ─▶ 7:3 拆分 ─▶ 装箱 ─▶ 校验
                                                          │
                                        ┌── ERROR ──▶ 阻断确认，回约束页
                                        └── 通过 ───▶ 确认 ──▶ 版本 v1（只读快照）
                                                                  │
                                            看板（今天/本周/全部）◀┘
                                                  │
                                       打卡 / 更正 / 备注（只追加）
                                                  │
                              逾期 ≥48h 或目标变化 ──▶ 调整 ──▶ 差异预览 ──▶ v2
```

管理员分支：维护课程与知识点 → 先修整批提交（成环拒绝）→ 资源关联 → 备份。

与质量保证计划的比较：D01 未制订独立的质量保证计划，实际以"覆盖率 100% + 交叉评审 + 真实模型评测"三条替代，效果可接受，但缺少**缺陷分级与回归清单**，导致修复后的复测依赖记忆（本次靠 `smoke.mjs` 脚本兜底）。

|---|---|---|
| 分层架构（api / services / db / core） | 全程 | **好**：服务层可脱离 HTTP 单测，是覆盖率能到 100% 的前提 |
| 规则优先、模型兜底 | 全程 | **好**：成本可控、可离线；规则命中的 7 条样本 0.01 s 完成，只有规则未命中才花钱 |
| 单一 `schema.sql` + 触发器维护不变量 | 全程 | **好**：只追加表由数据库强制，应用层写错也改不动历史 |
| 自研 md → docx 管线 | 文档阶段 | **好**：公式转 OMML、代码块保留缩进、表格与图题自动排版，节省大量手工排版时间 |
| 测试分层（逻辑走 mock，智能体走真实 API） | 全程 | **好，但曾引起争议**：一开始把智能体也走 mock，等于没测；改为真实评测后立刻暴露 3 个缺陷 |
| 前端组件化 + 设计令牌 | v1.1 | **一般**：重构后可用性与可访问性明显提升，但两套样式令牌并存，维护成本偏高 |
| 无 CI、无静态检查 | 全程 | **不足**：靠人工执行命令，合并前忘记跑测试的风险实际发生过一次（靠冒烟脚本兜住） |
| 无版本标签（tag） | 全程 | **不足**：交付版本只能靠提交哈希定位 |

表 3.4 缺陷原因分类

| 类别 | 缺陷 | 根因 | 占比 |
|---|---|---|---|

## 4 经验与教训

**做对的事**

1. **数据先于界面**：先把容量、拆分、装箱、校验做成纯函数并测到 100%，再做界面；后来前端整体重写，业务规则一行没改。
2. **规则优先、模型兜底**：既控制了成本与延迟（规则命中 0.01 s），也保证了断网可用；模型只在真正需要语义判断时才调用。
3. **同一份数据只算一次**：容量 C/B/C′ 只在一处计算，接口与界面都读同一个结果，避免了"页面显示 5%、接口返回 4.9%"这类问题。
4. **交付物自动化**：表题（108 条）、公式（29 处 display + 46 处 inline）、代码缩进、图片嵌入全部由脚本处理，Word 与 md 内容始终一致。
5. **演示数据可重建**：`seed.py` 一条命令重建 12 知识点 / 22 任务的完整演示库，答辩现场不会因为数据被改乱而翻车。

**教训**

1. **外部依赖必须真测，mock 只能测降级**。我们直到最后两天才接真实模型，一接就连爆两个缺陷（思考 token、JSON 围栏）。**教训：凡是有外部服务的功能，第一天就要有一条打到真实服务的冒烟用例。**
2. **同一个业务事实只能有一个口径，并且写在数据库上**。"完成"这件事在代码里按版本算、在数据库里按任务唯一，谁也不冲突，合起来就是矛盾的。**教训：业务不变量优先用约束表达，应用层判断必须与约束同源。**
3. **文档与实现不一致，比 bug 更难发现**。幂等键那条如果没写进 D06，错误就只是"体验差"；写进了 D06 就成了"实现违约"，评审必挑。**教训：文档里每一句"必须/应当"都要有对应测试，否则宁可写"暂不支持"。**
4. **重构前先固化"能力清单"**。前端重写丢了"解析方式标识"，因为没人列过"这个界面必须能看到什么"。**教训：重构的验收标准是旧能力清单全过，而不是新视觉稿好看。**
5. **估算要留出测试与文档的时间**。D01 估 5 000 行，实际 8 253 行；测试占 39% 的代码量，计划里完全没体现。**教训：按"源码 : 测试 : 文档 = 1 : 0.6 : 0.5"排期。**
6. **报告要写偏差，不要掩盖偏差**。本报告如实写了"编码提交滞后 5 天""缺陷密度 3.1/千语句""资源不能编辑"，这些反而是评审最认可的部分。

**给后续项目的建议**

表 4.1 经验与教训

| 建议 | 具体做法 |
|---|---|
| 先搭"一条真实链路的冒烟" | 第一天就跑通"登录 → 调一次真实模型 → 落库 → 界面显示" |
