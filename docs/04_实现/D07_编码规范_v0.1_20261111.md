## 1 目的

1. 指导开发组按统一风格编写与评审代码；
2. 便于成员之间读懂彼此的代码（本组 4 人、前后端并行）；

## 2 代码规范

### 2.1 有关命名

总原则：**名称表达"是什么/做什么"，不表达"怎么做"**；同一层概念用同一词根（如统一用 `constraint` 而非 `limit`/`rule` 混用）。

#### 2.1.1 包命名

表 2.1 包命名

| 层 | 规则 | 示例 |
|---|---|---|
| Python 包 | 全小写、单数、无下划线 | `app.core`、`app.db`、`app.api`、`app.services` |
| 前端目录 | 全小写、单数 | `src/lib`、`src/hooks`、`src/pages`、`src/components`、`src/styles` |
| 层职责 | 目录名即职责：`core` 基础设施、`db` 存储、`api` 路由、`services` 业务 | 不允许把业务逻辑塞进 `api` |

#### 2.1.2 类命名

- Python：大驼峰（`PascalCase`），名词或名词短语；数据容器用 `XxxInput` / `XxxResult` / `XxxSummary` 后缀。
  例：`ConstraintInput`、`NormalizedConstraint`、`CapacitySummary`、`SubmitResult`、`Draft`。
- 前端：React 组件用大驼峰且与文件名一致（`TaskCard.tsx` → `TaskCard`）；页面以 `Page` 结尾（`BoardPage`）。
- 自定义异常以 `Error` 结尾（`ValidationError`、`ProviderTimeout`），且继承项目内的基类。

#### 2.1.3 方法命名

- 动词开头、小写 + 下划线（`snake_case`）。
- 常用动词固定含义：

表 2.2 方法命名

| 动词 | 含义 | 示例 |
|---|---|---|
| `get_*` | 取单个对象，不存在抛错 | `get_course` |
| `list_*` | 取列表，空列表不抛错 | `list_resources` |
| `load_*` | 从库读原始行 | `load_concepts`、`load_edges` |
| `create_*` / `save_*` | 新建 / 覆盖式保存 | `create_concept`、`save` |
| `normalize_*` | 输入规范化（不改库） | `normalize_availability` |
| `expand_*` / `compute_*` | 纯计算 | `expand_slots`、`compute_capacity` |
| `submit` | 事件类写入 + 幂等 | `ProgressService.submit` |
| `build` | 聚合多个来源的读模型 | `BoardService.build` |

- 布尔返回用 `is_*` / `has_*`（`is_overdue`、`_has_done`）；不要用 `check_*`。
- 内部方法以单下划线开头（`_candidates`、`_write_version`），表示不对外。
- 前端回调与事件处理器用 `on*` 前缀（`onSelect`、`onCorrection`）；hook 一律 `use` 开头且大驼峰（`useBoard`、`useConfirmDraft`）。

#### 2.1.4 变量命名

- 小写 + 下划线；**不用**单字母（循环下标 `i` / `index` 除外）。
- 缩写词只保留全大写常量形式；变量里用小写（`cid`、`pid` 可接受，但 `concept_id` 更优先）。
- 集合用复数（`tasks`、`slots`、`edges`）；映射用 `*_by_*`（`code_by_concept`、`minutes`）。
- 前端：状态变量 `xxx` + `setXxx`；派生值不加 `use` 前缀；常量与后端保持一致命名。

#### 2.1.5 常量命名

- 全大写 + 下划线；定义在模块顶部或 `core/config.py`。
- 业务参数一律进配置类 `EngineConfig`（不散落在函数内），并在 `DEFAULTS` 中给默认值（D06 表 2.2 为唯一来源）。
  例：`STUDY_RATIO`、`BUFFER_RATIO`、`MAX_SLICE_SECONDS`、`DELAY_THRESHOLD_HOURS`、`BACKUP_KEEP`。
- 模块内私有常量同样全大写，但加前缀区分用途：`MAX_SEGMENTS_PER_DAY`、`EMPTY_AVAILABILITY`、`ALL_EXCLUDED`。
- 错误码是常量（`E1001` 等），只能通过 `core/errors.py` 抛出，禁止在业务代码里手写字符串错误。

#### 2.1.6 资源文件命名

表 2.3 资源文件命名

| 类型 | 规则 | 示例 |
|---|---|---|
| 文档 | `D<两位编号>_<名称>_v<版本>_<日期>.md` | `D06_详细设计说明书_v1.1_20261108.md` |
| 插图 | `<文档号>-<章>-<序>-<英文短名>.png` | `d11-4-03-board-today.png` |
| 脚本 | 动词 + 对象 | `seed.py`、`e2e_real.py`、`eval_agent.py`、`md2docx.py` |
| 数据库脚本 | 单一 `schema.sql`（不拆多份迁移，见 §5） | `scripts/schema.sql` |
| 测试 | `test_<模块或主题>.py` / `<组件>.test.tsx` | `test_capacity.py`、`TaskCard.test.tsx` |

#### 2.1.7 其他命名

- URL 路径：小写、连字符、复数名词（`/api/plans/{id}/drafts`）；资源标识用 `{xxx_id}`。
- JSON 字段：`snake_case`（`target_concept_id`、`actual_minutes`），前后端一致，**不转换**为驼峰。
- CSS 类名：小写 + 连字符，按"块-元素-状态"组织（`agenda-item`、`board-rail`、`cal-col`）；状态用 `data-*` 属性（`data-status="done"`）而非新类名。
- CSS 自定义属性统一 `--` 前缀，集中在 `product.css` 顶部（当前 37 个）。

### 2.2 有关注释

原则：**注释解释"为什么"，不重复"是什么"**（代码本身说明是什么）。

#### 2.2.1 程序文件头注释

每个 Python 模块首行必须有模块 docstring，说明职责与对应设计章节：

```python
"""课程资源维护与关联（对应 D02 F-05、AT-09、AT-10）。

规则：
- 资源必须属于同一门课；标题 1–200，类型四选一；
- url 必须是 http(s)，link 类型必须有 url；
...
"""
```

要求：

1. 第一行写"做什么"，括号里引用需求编号或设计章节号；
2. 若模块有非显然的规则或坑，紧跟一段要点列表；
3. 现状：34 个后端文件中 29 个已有模块 docstring，其余 5 个为 `__init__.py` 或极简入口。

#### 2.2.2 方法头注释

- 公开方法（对外或跨模块调用）必须有 docstring；内部方法可省略，但**算法类必须有**。
- 只写三类信息：参数约束、返回约定、副作用/异常。
- 关键算法用"为什么这么算"的注释，例：

```python
# 最小高度是按"百分比"兜底，不是按比例，否则短任务会被放大成整列
return {..., "heightPct": max((bottom - top) * 100, 2.2)}
```

- 禁止的注释：`# 循环`、`# 返回结果`、被注释掉的旧代码（用 git 历史代替）。

#### 2.2.3 关键点注释

以下位置**必须**有注释：

表 2.4 关键点注释

| 位置 | 内容 |
|---|---|
| 时间/时区换算 | 明确数据是 UTC 还是本地墙钟（本项目：存储 epoch 秒，接口返回本地墙钟字符串） |
| 浮点与取整 | 说明为何用 `Fraction`（`7/10` 直接乘会得到 62 而非 63） |
| 数据库约束的妥协 | 如"完成事实按 task_id 全局判定，与 `ux_done_once` 同口径" |
| 降级路径 | 说明超时/不可用/乱答各自的处理与原因码 |
| 安全相关 | 口令加盐、幂等键、越权返回 404 而非 403 的理由 |

## 3 格式规范

### 3.1 缩进

- Python / TS / CSS：**4 空格**（Python）、**2 空格**（TS/TSX/CSS/JSON/Markdown 表格对齐除外）。
- 禁止 Tab 字符；`json`/`yml` 统一 2 空格。
- 续行缩进对齐开括号内容，或使用悬挂缩进（二者择一，同一文件内保持一致）。

### 3.2 换行

- 行宽上限 **100 列**（当前最长 109 列，超限 3 行，见附录 A，需在下次提交前修正）。
- 函数之间空 1 行；类内方法之间空 1 行；模块级分节用 1 行空行 + 注释分隔。
- 文件末尾保留 1 个换行，不留多余空行。
- Git 落盘统一 LF（`.gitattributes` 未强制，Windows 下会出现 CRLF 提示，不影响内容）。

### 3.3 对齐

- 赋值号不强制对齐（避免 `=` 两侧大量空格造成 diff 噪声）。
- 字典/对象字面量：`:` 后 1 空格；多行时每行一个键值对，末项允许尾逗号（TS 必须）。
- SQL：关键字大写（`SELECT`、`WHERE`），表名字段名小写；多行 SQL 用字符串拼接并保持缩进可读。
- Markdown 表格：每行等宽管道符，列内容左对齐；表题在表上方单独一行（"表 x.y 名称"）。

## 4 数据库对象定义规范

### 4.1 表名命名规则

- 全小写 + 下划线，**单数**名词（`concept` 不是 `concepts`）。
- 前缀表达归属与角色：

表 4.1 表名命名规则

| 前缀 | 含义 | 示例 |
|---|---|---|
| 无前缀 | 主数据 | `app_user`、`course`、`concept`、`resource` |
| `plan_` | 计划域 | `plan_constraint`、`plan_task`、`plan_version`、`plan_draft`、`plan_validation` |
| `version_` / `task_` | 版本与片 | `version_task`、`task_slice` |
| 关联表 | 两侧名拼接，按字母序 | `concept_resource` |

- 命名不得使用保留字（`order`、`group`）；已有表共 16 张，新增表必须先在 D05 登记。

### 4.2 字段名命名规则

- 小写 + 下划线，单数；外键 = 被引用表主键名（`concept_id`、`plan_id`、`version_id`）。
- 主键统一 `<表名单数>_id`，`INTEGER PRIMARY KEY`（SQLite 自增）。
- 布尔字段用 `INTEGER NOT NULL CHECK (x IN (0,1))`，命名不带 `is_` 前缀（`in_scope`、`frozen`）。
- 时间字段：存储 epoch 秒（`start_epoch`、`end_epoch`）或 ISO 字符串（`created_at`、`occurred_at`），**同一表内不混用两种**；字段名必须能看出单位（`*_epoch`、`*_minutes`、`*_hours`）。
- JSON 字段以 `_json` 结尾（`availability_json`、`snapshot_json`、`payload_json`）。

### 4.3 索引命名规则

表 4.2 索引命名规则

| 前缀 | 含义 | 示例 |
|---|---|---|
| `ux_` | 唯一索引（业务硬约束） | `ux_current_plan`、`ux_done_once`、`ux_single_course` |
| `ix_` | 普通索引 | `ix_plan_owner`、`ix_slice_time`、`ix_event_task` |

- 索引名 = 前缀 + 表名缩写 + 字段缩写（`ix_vtask_task`、`ix_cr_resource`），长度尽量 ≤ 25 字符。
- 唯一索引必须能一句话说明业务含义（写进 D05 表 4.x）。

### 4.4 主键、外键命名规则

- 主键：`PRIMARY KEY` 直接写在字段行内；复合主键仅用于关联表（`concept_resource` 以 `(concept_id, resource_id)` 为主键）。
- 外键：`FOREIGN KEY (col, course_id) REFERENCES table(col, course_id)`，**带租户列**（`course_id`）保证跨课程引用不会串；当前共 18 个外键。
- 外键动作统一 `ON DELETE RESTRICT`（本系统不物理删除业务数据）。
- 复合外键必须显式声明被引用表的 `(列, course_id)` 唯一约束（`UNIQUE (resource_id, course_id)`）。

## 5 其他约定

表 5.1 其他约定

| 约定 | 内容 |
|---|---|
| Schema 管理 | 单一 `scripts/schema.sql` + `schema_meta` 版本号；不使用迁移框架；改表须同步 D05 与本文档 §4 |
| 只追加表 | `plan_version`、`version_task`、`task_slice`、`plan_validation`、`learning_event` 禁止 UPDATE/DELETE，由 13 个触发器强制；确需修正时追加新记录 |
| 错误处理 | 业务异常只抛 `core.errors` 中的类型；禁止 `except Exception: pass`；SQL 唯一约束冲突必须翻译成业务错误码，不得把 SQL 文本返回前端 |
| 日志 | 结构化 JSON，一行一条；必含 `request_id`；禁止记录口令、令牌、密钥与完整请求体 |
| 密钥 | 只从 `.env` 或环境变量读取；`.env` 永久在 `.gitignore`；仓库历史不得出现密钥 |
| 依赖 | 不新增运行时依赖完成任务（如 HTTP 用标准库 `urllib`）；确需新增须在组内说明理由并锁版本 |
| 测试 | 新功能必须同时提交测试；语句覆盖率维持 100%，不可达分支必须删除而不是注释 |
| 提交信息 | `<类型>(<范围>): <做了什么>`，类型用 `feat/fix/docs/test/chore/design`；一次提交只做一件事 |
| 评审 | 文档与代码交叉评审（写的人不自审）；数据库与接口变更须双方确认 |
