## 1 引言

### 1.1 编写目的

本计划用于明确「学径 StudyPath——课程学习规划辅助系统」的项目范围、任务分解、人员分工、进度安排、资源需求与风险对策，作为项目组内部的共识文件与检查依据。

预期读者：项目组全体成员、指导教师（评审）、课程验收人员。

本计划的具体作用有三点：

1. **对齐范围**：明确 4 周内做什么、不做什么，防止中途扩需求；
2. **对齐节奏**：把 120 学时分配到具体日期，每个阶段有可检查的成果物；
3. **对齐责任**：每项任务有唯一负责人，避免"都管都不管"。

### 1.2 背景

**a. 待开发的软件系统名称**

学径 StudyPath —— 课程学习规划辅助系统。

**b. 任务提出者、开发者与用户**

| 项 | 说明 |
|---|---|
| 任务提出者 | 《软件工程综合实训》课程组 |
| 开发者 | 软件工程 2 班 第 6 组（王昱涵、李鸿佑、李俊达、项奕乔） |
| 用户 | 修读单门课程的高校学生（主用户）、课程管理员（内容维护） |
| 运行环境 | 本地部署 Web 应用，浏览器访问，SQLite 存储 |

**c. 与其他系统的关系**

本系统为独立系统，不与教务系统、在线学习平台对接。唯一可选外部依赖为大语言模型服务，通过 Provider 接口调用，可切换为本地 Mock，切换后功能完整可用。

**问题背景**：学生在单门课程中普遍面临"资源有、时间不够、不知道从哪开始"的问题。课程大纲给出的知识点清单是**知识结构**，不是**时间计划**；把前者翻译成后者，目前完全依赖学生个人经验，且缺少校验手段——计划排不排得下、会不会和先修冲突，只能等做不完才发现。

本系统把这一步显式化、可计算化：课程管理员维护结构化的课程内容，学生给出目标与时间约束，系统用程序算出可执行计划，并在执行过程中检测延后、给出调整方案、保留版本与原因。

### 1.3 定义

| 术语 / 缩写 | 释义 |
|---|---|
| 知识点（Concept） | 课程内容最小学习单元，含难度、参考学习时长、学习目标 |
| 先修关系 | 知识点间的有向依赖，A → B 表示学 B 前须完成 A；本系统仅 AND 语义 |
| 时间容量 | 学生可用时间总和；容量校验即"任务需求时长 vs 可用时长" |
| 计划任务 | 计划最小执行单元，一个知识点拆「学习」「练习」两类 |
| 计划版本 | 每次确认或调整生效时生成的不可变快照，含原因与差异 |
| 智能体（Agent） | 承担单一职责的大模型调用单元 |
| 确定性引擎 | 不含大模型、结果可复现的计算模块（排程引擎、校验引擎） |
| LLM | Large Language Model，大语言模型 |
| WBS | Work Breakdown Structure，工作分解结构 |
| MVP | Minimum Viable Product，最小可行产品 |
| JWT | JSON Web Token，登录凭证格式 |
| SSE | Server-Sent Events，服务端推送 |

## 2 项目概述

### 2.1 工作内容

项目须完成以下 9 项主要工作：

1. 需求获取与建模，编写《软件需求说明书》与《数据要求说明书》；
2. 概要设计与数据库设计，编写《概要设计说明书》《数据库设计说明书》；
3. 详细设计，编写《详细设计说明书》（含排程算法与校验规则设计）；
4. 编码实现：后端服务、排程引擎、校验引擎、四类智能体、前端界面；
5. 编写单元测试与接口测试，形成《测试计划》《测试分析报告》；
6. 编写《编码规范》《模块开发卷宗》《用户手册》《操作手册》；
7. 部署与演示准备（含离线 Mock 模式），编写《软件维护报告》；
8. 过程管理：《开发进度月报》（周报）、《项目管理方案》、阶段评审记录；
9. 实训总结与答辩（小组总结、个人总结、PPT、7 分钟演示）。

### 2.4 验收标准

| 维度 | 验收标准 | 对应考核项 |
|---|---|---|
| 代码 | 可一条命令启动；主流程（登录→设定约束→生成计划→校验→确认→打卡→调整→查看版本）全部走通；关键算法有单元测试且全部通过 | 系统功能实现（20 分） |
| 文档 | 18 类文档齐备，格式符合模板；文档描述的功能可在系统中演示；需求—设计—代码三者一致（以需求追踪矩阵核查） | 阶段性开发文档（30 分） |
| 过程 | 周报、评审记录、任务分配记录完整；每次评审有结论与整改项 | 实训过程跟踪与角色贡献（30 分） |
| 答辩 | 7 分钟内完成演示；能回答设计取舍（为何校验由程序算而非模型算）；有独立见解 | 答辩（20 分） |

**功能验收的最小闭环（MVP）**：即使时间紧张，以下 5 条必须可演示，否则视为未达验收底线：

1. 管理员能录入知识点与先修关系，并能被学生端看到；
2. 学生能设定目标、截止日期、可用时间；
3. 系统能生成计划，并**当场报出容量不足或截止不可达**；
4. 学生能确认计划并打卡；
5. 调整后能看到新旧版本差异与原因。

**技术难点（需重点关注）**

1. **时间装箱与先修约束的联合求解**：既要满足拓扑序，又要在离散可用时段内装下，属于带优先约束的装箱问题。策略是先拓扑分层、层内按难度排序、再按可用时段贪心填充，冲突时后置到下一时段并记录告警。不追求最优，追求**可解释、可复现**。
2. **"程序算、模型说"的边界划分**：一旦把校验交给模型，结果不可复现且无法单测。本项目在架构上强制分离：引擎返回结构化结果，模型只负责把结果翻译成人话。此约束写入编码规范。
3. **计划调整的差异计算**：任务有 ID、时段、时长三个可变维度，需要定义"移动/缩放/增删"的判定规则，否则版本对比会退化成"全都变了"。

### 5.2 测试计划

| 层次 | 范围 | 方法 | 责任人 |
|---|---|---|---|
| 单元测试 | 排程引擎、校验引擎、约束校验、差异计算 | pytest，覆盖正常/边界/异常 | 成员 B |
| 接口测试 | 13 项功能对应的 20 余个接口 | pytest + httpx，含鉴权与越权 | 成员 B |

关键边界用例：截止日期为明天、可用时间为 0、目标是已掌握知识点、先修成环、知识点为孤立点。

### 5.3 质量保证计划

1. **编码规范**：命名、注释、异常处理、日志四条硬性要求，违反者评审不通过（见 D07）；
2. **代码评审**：每个功能分支合并前由非作者评审，关注"是否违反'程序算、模型说'的边界"；
3. **每日构建**：每日收工前跑一次全部单测，红灯不过夜；
4. **文档一致性**：每周五检查需求追踪矩阵，确认每条需求有实现、每个实现有出处；
5. **缺陷管理**：所有缺陷记录在 `docs/09_过程记录/缺陷登记表.md`，含发现时间、严重级、复现步骤、修复状态。

### 5.4 配置管理计划

| 项 | 约定 |
|---|---|
| 仓库 | Git，主分支 `main` 受保护，禁止直接推送 |
| 分支 | `feature/<模块>-<简述>`、`fix/<问题>`；合并前须通过自测 |
| 提交信息 | `<类型>(<范围>): <描述>`，类型 ∈ feat/fix/docs/test/refactor/chore |
| 版本标记 | 里程碑打 tag：`m1-需求基线`、`m2-设计基线`、`m3-功能冻结`、`v1.0-交付` |
| 配置项 | 源码、文档、种子数据、部署脚本；二进制与依赖不入库 |
| 环境隔离 | `.env` 不入库，提供 `.env.example` |

### 5.5 安全保密计划

1. 密钥（数据库口令、API Key、JWT SECRET）仅通过环境变量注入，禁止写入代码与文档；
2. 演示数据使用虚构学生信息，不包含真实姓名、学号；
3. 仓库不公开（或交付前清理历史中的敏感信息）；
4. 学生数据仅用于本系统，不向第三方传输；调用大模型时只传知识点与时长，不传个人身份信息。

### 5.6 文档管理计划

1. 所有文档以 Markdown 为主稿，存于 `docs/`，按 `D<编号>_<名称>_v<版本>_<日期>.md` 命名；
2. 需提交 Word 版时由主稿导出，不维护双份内容；
3. 每份文档末尾设"变更记录"表，任何修改追加一行；
4. 文档责任人：D01/D04/D06 由组长负责，D02/D03/D05 由成员 B 负责，D11/D12 由成员 A 负责，其余按 2.3.2 分配；
5. 文档评审与代码评审同步进行，评审意见记入 `docs/09_过程记录/评审记录.md`。
